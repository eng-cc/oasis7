# 📋 PRD 审查 Checklist 模板（专业可执行版）

> 使用方式：
>
> * 按本次范围使用适用问题；✔ / ❌ / ⚠ / N/A 与后附评分均为可选审读辅助，不要求固定逐项输出。
> * N/A 说明具体理由、范围及重要未覆盖义务；本清单不另设评审批准步骤，适用合同本身的例外/验证要求仍须满足。
> * 实施与评审遵循[开发流程规范](../../doc/engineering/workflow/source-of-truth.md)；本清单的质量判断不增加准入、固定材料或完成条件。

---

# 一、目标与背景（Why 层）

## 1. 业务目标是否明确？

* [ ] 是否明确说明本期解决什么问题？
* [ ] 是否定义成功指标（可量化）？
* [ ] 是否与公司/项目阶段目标一致？
* [ ] 是否说明优先级来源？

**否决条件：**

> 如果无法明确问题与预期结果，先澄清受影响范围再推进依赖该判断的实现；不以此阻止无关已授权工作。

---

# 二、用户与场景（Who / When）

## 2. 用户定义是否清晰？

* [ ] 是否明确目标用户是谁？
* [ ] 是否区分主用户与边缘用户？
* [ ] 是否定义使用场景？
* [ ] 是否说明频率与关键路径？

**风险信号：**

> “所有用户都需要” → 通常不够聚焦。

---

# 三、范围定义（Scope Control）

## 3. 是否定义功能范围？

* [ ] 是否列出本期功能清单？
* [ ] 是否明确 Out of Scope？
* [ ] 是否避免隐性功能（未写但默认存在）？
* [ ] 是否有版本拆分说明（如 v1/v2）？

**否决条件：**

> 如果边界不清晰 → 必然 scope creep。

---

# 四、功能规格（What）

## 4. 功能是否可直接实现？

* [ ] 每个功能是否描述完整？
* [ ] 是否有交互流程说明？
* [ ] 是否明确字段定义？
* [ ] 是否描述所有按钮行为？
* [ ] 是否定义状态变化逻辑？
* [ ] 是否描述排序规则 / 计算规则？
* [ ] 是否明确权限控制逻辑？

**核心判断：**

> 研发是否无需口头补充即可开发？

---

# 五、异常与边界（Edge Cases）

## 5. 是否覆盖异常情况？

* [ ] 网络异常如何处理？
* [ ] 空数据如何展示？
* [ ] 权限不足如何反馈？
* [ ] 接口超时如何处理？
* [ ] 并发冲突如何处理？
* [ ] 数据异常如何兜底？

**否决条件：**

> 如果只写理想路径 → 不合格。

---

# 六、非功能需求（NFR）

## 6. 是否定义性能与约束？

* [ ] 是否定义性能要求？
* [ ] 是否定义兼容性要求？
* [ ] 是否定义安全要求？
* [ ] 是否定义数据规模预期？
* [ ] 是否定义可扩展性约束？

---

# 七、可测试性（Testability）

## 7. 是否可写测试用例？

* [ ] 是否定义验收标准？
* [ ] 是否定义完成标准？
* [ ] 是否定义数据验证方式？
* [ ] 是否定义回归影响范围？

**核心判断：**

> QA 是否可以仅根据 PRD 写测试用例？

---

# 八、逻辑一致性（Consistency）

## 8. 是否前后一致？

* [ ] 是否存在逻辑冲突？
* [ ] 是否存在目标与设计不匹配？
* [ ] 是否存在自相矛盾？
* [ ] 是否与历史版本冲突？

---

# 九、依赖与影响分析（Impact）

## 9. 是否识别依赖？

* [ ] 是否明确依赖系统？
* [ ] 是否明确接口依赖？
* [ ] 是否评估影响模块？
* [ ] 是否评估数据迁移？
* [ ] 是否识别上线风险？

---

# 十、决策透明度（Decision Record）

## 10. 是否记录关键决策？

* [ ] 是否说明方案选择原因？
* [ ] 是否记录被否决方案？
* [ ] 是否有数据支持？

---

# 🏗️ 十一、文档树一致性与结构约束（Documentation Architecture）

这一部分专门用于 **约束大型项目的文档体系**，避免文档失控、重复定义、结构腐烂。

建议将其设为 **关键项**。

---

# 十一、文档树一致性与结构约束

## 11.1 归属检查（Document Placement）

* [ ] 本 PRD 是否明确归属于某个模块目录？
* [ ] 是否符合文档树层级规范？

**否决条件：**

> 文档归属不清 = 未来结构必然混乱。

---

## 11.2 单一事实源（Single Source of Truth）

* [ ] 本文是否重复定义已有模型？
* [ ] 是否复制粘贴其他模块的字段或状态？
* [ ] 是否引用已有定义，而不是重写？

例如：

❌ 在订单模块再次定义用户字段
✅ 引用 user_system/domain_model.md

**否决条件：**

> 出现重复定义 = 必须修改。

---

## 11.3 跨模块引用规范

* [ ] 是否清晰标注跨模块依赖？
* [ ] 是否引用接口文档，而非嵌入逻辑？
* [ ] 是否定义调用边界，而非实现细节？

核心原则：

> 本模块只描述“调用”，不描述“被调用模块内部逻辑”。

---

## 11.4 抽象层级检查（Layer Discipline）

* [ ] 战略文档是否出现实现细节？
* [ ] 模块 PRD 是否出现系统级讨论？
* [ ] 是否混合 UI 描述与架构决策？

规则：

| 层级  | 允许写什么 | 禁止写什么  |
| --- | ----- | ------ |
| 战略层 | 目标、原则 | 字段级逻辑  |
| 系统层 | 模块关系  | 具体按钮行为 |
| 模块层 | 功能细节  | 公司战略   |

如果违反 → 必须拆分。

---

## 11.5 依赖可追溯性（Traceability）

oasis7 内容检查的规范 finding 按[增量检查边界](../../doc/engineering/doc-governance/product-documentation-standard.design.md#advisory-content-checks)在 PR 新增或实质修改的适用文档范围内阻断 CI，未触达历史只警告；本清单的人工语义判定不等于检查器能自动证明的事实，输入/执行错误和既有完整性检查仍失败。

* [ ] 是否可从本 PRD 追溯到系统总览？
* [ ] 是否标注版本号？
* [ ] oasis7 新增或实质修改的稳定要求是否按[跨层要求与验证映射](../../doc/engineering/doc-governance/cross-layer-requirements-traceability.design.md#global-requirement-trace)复用唯一声明的全局 Trace ID，并保留本地条款 ID 和真实链接？
* [ ] 是否能人工追到适用系统设计与已有 Task/PR 的本次范围和实际证据；尚未形成或确实不适用的层级是否如实说明？不要求为此新建 Issue、回填未触达存量或增加准入/合入门禁。

Trace refs: O7-REQ-276983b3-3187-405e-8453-e2785f01c5e6；以上核对消费既有全局要求追踪规范，只读查询工具已有有界聚合与重复声明诊断，但不代表完整性、全仓唯一性或功能完成证明。

* [ ] 每个本次触达的产品功能点是否按[双状态规范](../../doc/engineering/doc-governance/product-documentation-standard.design.md#feature-design-implementation-status)分别记录系统设计与实现状态，并链接准确设计条款、适用 Trace ID 和 Task/PR/实际验证证据？“部分”是否列剩余范围，“已验证”是否有固定基线、环境与验收范围，要求变化后是否重核？详细过程仍在 Task，原有追踪表列保持不变。

理想结构：

```text
Module PRD
  → System Overview
  → Related ADR
  → Interface Contract
```

---

## 11.6 变更影响控制

* [ ] 本次修改是否更新依赖文档？
* [ ] 是否列出受影响模块？
* [ ] 是否更新接口版本？

核心原则：

> 修改一个模块，不允许 silently 影响其他模块。

---

## 11.7 规模控制（Anti-Bloat）

* [ ] 单文档是否超过合理阅读长度？
* [ ] 是否应该拆分为子文档？
* [ ] 是否存在大量历史废弃内容未清理？

原则：

> 文档 > 1000 行必须评估拆分。

---

## 11.8 反流水账（PRD vs Project vs Devlog）

* [ ] PRD 描述目标态规格（Why/What/Done）及有依据的功能设计/实现状态摘要，不写任务拆解或详细进度叙述。
* [ ] 既有 Task/PR（Issue 按需）描述任务与执行（How/When/Who），不重写需求规格。
* [ ] `doc/devlog/YYYY-MM-DD.md` 仅记录当日过程（时刻、完成内容、遗留事项），不定义需求。
* [ ] `Critical User Flows` 描述系统/用户/操作者行为与状态变化，不描述“改文档流程”。
* [ ] `Acceptance Criteria` 描述可复现验证结果（行为/不变量/指标/测试），不是文件清单。
* [ ] `Roadmap/Milestones` 描述能力交付阶段（MVP/v1.1/v2.0），不是日常进度列表。

**否决条件：**

> 任一检查项为“否”即不通过 11.8。

# PRD 质量结论与风险处置

质量结论说明所审版本、适用范围、真实阻断问题及处置，不以全绿、分数或固定字段决定实施资格。

* 目标不清、边界未定义、缺少可验证验收，以及真实正确性、安全或数据丢失风险，按适用产品/专业合同与开发流程修复或以事实证明不适用；依赖这些判断的实现不得带着未解决的阻断缺口继续。
* 真实 N/A 解释理由与范围，不能用不适用掩盖缺失义务；本清单不新增 N/A 批准程序。
* 非阻断建议可以说明理由后不改，不自动创建后续任务，也不强制负责人/截止时间或延期表单。
* 适用的独立评审、必要检查与既有强制合同保持有效；无关已授权工作可继续。

# 📊 可选：量化评分模型（会议用）

| 模块    | 分值 |
| ----- | -- |
| 目标清晰  | 10 |
| 范围清晰  | 15 |
| 功能完整  | 20 |
| 边界覆盖  | 15 |

70–85 → 可优化

# 🧠 高级判断法（高手用）

问三个问题：

1. 如果产品经理离职，这个 PRD 是否还能被正确实现？
2. 如果半年后复盘，是否能看懂当时的决策逻辑？
3. 如果发生线上事故，是否可以从 PRD 追溯原因？

如果答案是否 → PRD 不成熟。
