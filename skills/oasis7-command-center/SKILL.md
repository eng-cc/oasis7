# Oasis7 项目指挥看板

帮助项目负责人回答：要达到什么、进展到哪里、依据哪些决定、现在需要处理什么。用现有事实生成视图，让日常使用减少翻文档和追问的成本。

本 Skill 提供看板方法，不定义新的开发流程。遵循当前仓库的 `doc/engineering/workflow/source-of-truth.md`；不增加任务准入、审批、生命周期、回执或交付条件。

## 先按请求确定动作

| 用户请求 | 交付与写入范围 |
| --- | --- |
| 构建、定制、修复看板 | 实现并验证看板及必要数据接入；沿用当前项目开发方法 |
| 查看、刷新、汇报进度 | 读取事实，更新已有派生视图或给出简报；不创建任务、发评论、改业务状态 |
| 记录、修改一项决策 | 在用户已授权范围内更新对应权威文档，随后更新索引；保留理由和替代关系 |
| 启动、继续、追加指令、停止开发任务 | 核对明确目标与实际可用适配器，在已有授权内执行并回读结果 |
| 只要设计方案或 Skill | 交付所要求的方案或 Skill，不顺带实施应用 |

已有授权持续有效。只有影响具体决定的缺失信息才需要提问；先完成不依赖该信息的工作。查看状态不意味着授权启动新的 Codex、外部模型任务、合入或部署。

## 定位当前来源

1. 读取 [项目入口地图](references/project-map.md)。确认目标为 `eng-cc/oasis7`；本地从实际 Git 根目录和工作树识别仓库，远程读取固定本轮已解析的提交。记录文档版本与查询时间，不能把历史快照称为最新 main。
2. 读取当前 `AGENTS.md`、开发流程规范和根 `README.md`。仅继续读取本任务相关的产品、专业域或测试文档；用 `rg` 找标题和路径，避免全仓全文加载。
3. 从 `doc/core/prd.md` 的“当前阶段交付目标与全局 P0”读取近期目标，从产品入口读取长期方向；不要把文件开头的历史里程碑当作当前路线图。
4. 按事项的主责条款和显式后继关系确定规范效力。文档修改时间、审计轮次、文件名和模型记忆不能单独决定优先级。无法消解的冲突展示来源及影响，不为无关工作增加阻塞。
5. 从 Git、PR、实际 CI 和评审读取交付事实。Issue/Project 按需关联；只有 PR 的工作也是完整有效的展示对象。分页不完整、离线或权限不足时说明覆盖范围，保留可用结果。
6. 将上传旧稿、历史 `.pm` 材料与当前规范区分。附件中的 `world-rule.md` 和旧 `agent_world_*` 命名不能固定为现行入口；通过当前文档导航找到接收条款。游戏世界实体与开发 Codex 会话使用不同身份与状态。

## 建立四个主要视图

| 视图 | 默认展示 |
| --- | --- |
| 方向与进度 | 当前阶段、长期方向、里程碑依赖、下一交付、已验证结果和阻塞；支持下钻到条款与 PR |
| 规范与决策 | 当前适用的规则、范围、理由、来源版本、待定问题和被替代的决定；原文可打开 |
| 开发执行 | 任务与 PR、开发会话、工作分支、最近活动、等待输入、失败或中断；标明可观察范围 |
| 待我处理 | 一个具体问题、必要背景、可选方案、建议及理由、受影响工作和处理入口 |

按 [视图与数据约定](references/view-model.md) 实现来源关联、进度和缺失状态。业务事实沿用原始来源；仅新增必要关联、视图偏好和可重建的读取缓存，不形成新的任务或规则权威。

## 构建或修改看板

1. 先读 [客户端形态与首版范围](references/desktop-client.md)。默认交付 macOS 优先的独立桌面客户端，由应用管理本地服务；浏览器界面用于开发预览。检查现有看板、用户指定宿主和目录说明，复用适合的实现并明确代码落点；沿用用户明确指定的交付形态。不要把开发会话自动放进公共站点或玩家 Viewer。
2. 读取 [技术选型决策](references/technology-decision.md) 和 [客户端架构](references/client-architecture.md)。当前推荐基线是 Tauri 2 + Rust 核心 + SolidJS/TypeScript；核对当前源码、依赖与用户约束后沿用，出现分册列明的变化再重评。此项目有纯静态 `site/` 和 Solid.js Viewer；不为看板改造世界运行时。UI 设计 Skill 已可用且适合时按需使用，缺失时按本 Skill 的信息层级与状态要求继续。
3. 先贯通“真实来源 → 规范化展示对象 → 页面”：接入文档与 GitHub，完成四视图、来源下钻和缺失状态。未接入的 Agent 区明确显示未连接；演示数据仅放在标明的演示入口。
4. 再按用户范围接入开发会话，读取 [Codex 接入边界](references/codex-integration.md)。复用现有可用接口；需要新适配器时仅实现必要范围。页面刷新不触发新的模型运行。
5. 在真实适配器可用且用户要求时加入操作。对不可用动作显示原因；不制作点击后伪造成功的按钮，不通过改本地缓存宣称远端任务或会话已改变。
6. 让常用信息便于扫读：紧凑列表或表格、明确的当前重点、按需展开详情、规范搜索、键盘焦点，以及加载/空白/错误/过期状态。高密度信息优先于装饰性指标卡；不把进度包装成无依据的百分比。

实施、调试、验证、评审按需复用 `.agents/skills/README.md` 中现有方法，不串成固定角色链。一个清楚目的尽量在一个 PR 原子完成；只读查询不需要为此创建 Issue、分支或远程记录。

## 刷新、决策与执行

- 刷新时读取源数据的实际变化，仅更新受影响的派生内容；展示最后成功读取时间和当前异常，不把读取失败变成“没有任务”。没有现成看板且只要求简报时，直接给简报。
- 汇报时依次写当前目标、变化与交付、阻塞/待决定、下一步、来源及未覆盖范围。把模型归纳标为归纳，保留事实入口。
- 记录决定时先找对应主责文档，优先更新既有条款或决策记录。用户本轮明确决定按其授权范围执行；尚未回写规范时标明“用户已决定，规范待同步”，不能谎称规范或实现已经同步，也不能伪造批准时间。
- 仅在用户要求记录且确无承载位置时创建最小决策文档，按当前文档规范放置。记录问题、决定、理由、范围、来源和后继关系即可；不另建通用决策登记系统。
- 执行看板动作前核对仓库、环境、目标 ID 和当前状态，复用有效授权与项目操作保护。结果不确定先查询，避免重复启动或重复写入；失败只影响依赖它的动作。

## 验证与交付

对实际改动执行最小有效验证。界面变更按当前 `testing-manual.md` 选用适用的 UI/Web 验证；新增数据合并或操作逻辑时覆盖最可能导致误导或重复执行的情形，不为纯文本 Skill 额外跑整个项目 CI。

重点核实：只有 PR 的任务能出现；文档 `active` 不冒充已实现；历史/过期结果可辨认；GitHub 暂不可用不清空已知事实；同一分支的不同会话不覆盖；会话结束不自动完成目标；来源链接能打开。适用项验证完成后停止扩展测试。

交付说明实际做成的内容、入口/调用方法、数据覆盖范围、验证结果及仍未接入的能力。按当前工作类型区分“Skill 已保存”“页面已实现”“代码已合入”“目标已验收”，不互相代称。
