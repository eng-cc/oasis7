# 时间表巡检与协调

本文件是每轮巡检的执行约定，不是 OpenAI 自动识别的心跳配置或已经部署的程序。时间点只在 [SCHEDULE.md](SCHEDULE.md) 维护，权限沿用 [AUTONOMY.md](AUTONOMY.md)。主 Agent 只协调，所有时间表事项交给真实 subagent。

## 接入前核实

运行器必须具备实际 20 分钟周期、授权的 GitHub 读取、跨轮持久状态、原子防重复派工、可查询的 subagent 任务及结果、通知能力。记录真实触发器 ID、采用的规则版本、时区、状态后端和激活时间；缺任何一项都不能宣称巡检已启用。

当前 ChatGPT 内置周期任务最高每小时一次，不能直接承载此处的 20 分钟要求；不拆多个小时任务绕过频率限制，不用循环等待假装常驻。接入新的外部运行器/模型服务须另行核对能力和授权。本 PR 只定义约定，不实现或部署运行器，未产生真实任务 ID 或执行记录。

## 一轮只做这些事

1. 读取当前时间和已经采用的规则版本。从同一提交读时间表、任务说明及权限边界；不得因 main 或待审 PR 多了一项就自动扩大任务范围。版本读取失败时不派新任务，可继续核对已经明确授权且有完整快照的在途任务。
2. 读取持久状态，先核对在途子任务、保存已返回的报告和待发通知。无法读取状态时不能把它当成“尚未执行”，暂停新派工并报告阻塞。
3. 按时间表展开从激活日到现在的每日实例，筛选 `scheduled_at <= now` 的事项。未到期不派；到期实例须同时满足尚未成功/终结、无在途任务、未暂停、重试条件满足以及仍在授权范围内。
4. 按计划到期时间从早到晚，在上限内原子认领实例；持久保存派工意图后才启动 subagent。空巡检直接结束，不启动一个子任务去判断“要不要启动子任务”。
5. 给 subagent 明确的任务包，确认真实子任务标识后记录运行中。本轮不必原地等待耗时分析；由运行器后续回调或下一次真实巡检收结果，不能以一句“继续后台处理”代替这些能力。
6. 主 Agent 核对报告的日期、来源、范围和完成情况，保存真实结果后更新状态，并按 [REPORTING.md](REPORTING.md) 汇总。主 Agent 不代做 CI 数据采集、统计或根因分析。

## 持久状态与防重复

复用实际运行器的私有持久存储，不使用聊天记忆、临时沙箱文件或 Git 提交充当执行账本。至少保存：`occurrence_key`、计划时间/时区、采用的配置提交、状态、尝试次数、派工幂等键、子任务 ID、更新时间、报告引用、最近错误及通知状态。首次初始化须能区别于存储丢失；状态不明时先恢复记录，不从空库重新派完全部任务。

`occurrence_key = 仓库 / 时间表稳定 ID / 计划本地日期`。每键只能原子认领一次；并发巡检须使用唯一约束、事务或 compare-and-set，不能只靠先读后写的提示词。运行器若不能提供该保证，就不启用自动派工。

| 状态 | 下一轮处理 |
| --- | --- |
| `pending` | 到期且有名额时认领 |
| `dispatching` | 先按已保存的幂等键核对是否已创建；结果不明时不重复启动 |
| `running` | 查询原有子任务；仍在执行就继续跟踪，不重派 |
| `succeeded` | 已保存完整报告；当天不再执行，仅处理未完成通知 |
| `partial` | 已交付带限制的报告；当天不自动重跑，不当成完整成功 |
| `failed` | 已确认原任务结束，且属于可重试故障时按上限重试；其他情况保留失败 |
| `blocked` | 权限、状态、工具或结果不明；前置恢复后先协调已有结果，再决定是否派工 |
| `cancelled` | 用户停止或事项已撤销；不自动重新启动 |

创建子任务的返回丢失时，先按幂等键查询真实结果；无法查询或不能证明未创建则保持 blocked，不盲目重试。一次认领记录绑定一次尝试；提交版本变化或主 Agent 重启不生成另一个实例。

只有 subagent 真正结束并返回可读取的报告，才可标记 succeeded/partial；“已派出”“模型说完成”或只有健康检查不够。保存报告和结果状态要可恢复；通知与分析分别去重，通知失败只补通知。发送结果未知时先核对已有消息，不无限补发。

## 并发、重试与停止

初版最多同时运行 2 个子任务，每次巡检最多新派 2 个，每实例最多 2 次尝试（含首次）；子任务不再递归派工。权限/数据不足交付 partial 或 blocked，不每轮重新分析；只有已确认结束的临时故障才在下一轮重试。设置执行上限 60 分钟，但到时先查询/停止原任务并确认终止，不能因超时或状态租约过期直接启动第二份。运行器必须能落实这些执行上限；需要新服务或新增费用时按 AUTONOMY 核对授权，不以时间表自动扩大预算。

暂停时间表项或收到停止要求后，不派新任务、不重试；按实际能力停止在途子任务并核对结果。无法确认已停止时保留真实在途状态并报告，不伪记 cancelled。清理或恢复不得删除防重复记录；配置变化不提升权限、并发或费用上限。

## 子任务说明模板

```text
你是时间表任务的执行 subagent，主 Agent 只负责协调。
仓库：eng-cc/oasis7；实例键：<occurrence_key>。
计划时间及任务日期：<scheduled_at / timezone / local_date>。
统计窗口：<window_start_inclusive, window_end_exclusive>；不要按实际补跑日重算。
采用的工作约定：<config_commit>；任务说明：<该提交内的任务文件>。
读取所需 GitHub 来源，记录实际查询时间、版本、分页及未覆盖范围。
仅做本项分析，不写仓库/评论、不重跑或取消 CI、不合入或部署、不再派工。
遵守已批准模型/预算和 60 分钟执行上限；缺关键条件如实交付限制，不伪造完成。
返回中文报告、来源链接、覆盖范围、完成/部分/失败结论，交给主 Agent 汇总。
```

任务创建时由运行器注入已有授权、实际执行限制与必要文件内容/可读取引用；模板中的占位符不视为已经完成派工。

## 行为试用场景

以下是接入后的验收案例，不是当前已经通过的运行记录，也不是仓库合入新门禁。

| 场景 | 期望 |
| --- | --- |
| 12:40 / 13:00 / 13:20 各巡检一次 | 12:40 不派；13:00 派一次；13:20 跟踪原任务或读已完成结果 |
| 13:00 漏触发，13:20 才恢复 | 补派同一天实例，不漏执行 |
| 两轮同时发现同一到期项 | 只有一个原子认领成功，不重复启动 |
| 任务跨越多个巡检间隔 | 保持同一子任务，不因未完成重复派工 |
| 派工响应丢失 / 主 Agent 重启 | 先读取持久记录并协调真实子任务，不盲重试 |
| 前一天未执行，跨日恢复 | 按旧计划日期补跑，CI 窗口不变；新日期实例独立去重 |
| 缺状态存储、subagent 或权限 | 报告具体阻塞；主 Agent 不代跑，实例不记成功 |
| 已有报告但通知失败 | 补通知，不再次分析 CI |
| 时间表改文案、暂停或用户停止 | 不重跑已完成项；暂停/停止阻止新派工并核对在途状态 |
