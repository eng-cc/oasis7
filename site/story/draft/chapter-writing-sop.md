# 《绿洲 2076》章节写作 SOP v0.3

本 SOP 根据第一卷第一章 `CH-001` 到 `CH-012` 的试写、调研、复审、最终五方审稿和 v0.8.1 极小润色经验整理，并补充完成一卷后的卷级审阅经验，用于后续章节从章节卡进入正文、审稿、补丁、复审和卷级体检。

## 适用范围

- 适用于第一卷正文草稿写作，尤其是从已确认章节卡进入新章节试写时。
- 适用于 2000 字以上、包含多个场景 / 多组老人-Agent / 生产线和情感线交织的正文。
- 不适用于单句设定补充、人物命名或纯聊天式头脑风暴；这些应先回到 `background/`、`characters/`、`timeline/` 或 `chapter-cards/`。

## 输入条件

开始写正文前，必须具备以下材料：

1. 对应章节卡已存在，且每场至少有 `CH-*`、`TL-*` 和主要 `CHAR-*`。
2. 本章或本阶段的社会口味 / 情感需求调研已存在，且结论写回 `site/story/research/` 对应文件；短调研写入 `research-notes.md`，单章专项调研写入 `volume-XX-chapter-YY-research.md`，跨章素材库可独立建档。
3. 本章情感胜利只定义到本章最低尺度，不提前吃掉卷末胜利。
4. 本章生产目标明确，能回答它如何推进“采矿 -> 冶炼 -> 零件打印 -> Agent 维修坞 -> 娱乐设施最低试运营”。
5. 本章人物功能边界明确，尤其区分：
   - 宋清岚 / 小穹：邀请伦理和低压力参与。
   - 周砚屏 / 应声：反馈是否被安心接收。
   - 林问秋 / 尺素：把愿望翻译成可共同选择的版本。
   - 罗衡 / 榫七：等待理由、承诺账本和维护排程。
   - 陈照野 / 留帧：保存真实痕迹，不包装失败。
   - 许映舟 / 砾光：远程身体、连续关系和现场伙伴感。
6. 确认禁区：不写 AI 反叛、公司阴谋、老人苦难、资源竞技、赛博黑暗风、贫富排名或利益冲突驱动。
7. 如使用互联网打工人痛点或梗素材，先确认 `internet-worker-hardship-meme-bank.md` 或等效调研文件；正文只转译情绪和反差，不直接复刻现实公司、事故或苦难案例。

## 标准流程

### 0. 社会口味调研

写正文前先做“口味校准”。调研不是追热点，也不是让故事改成迎合市场的题材，而是确认本章要写的情感需求仍然能被当下读者理解。

调研触发条件：

- 开始新卷、新章或关键情感节点前。
- 现实社会口味可能变化时，例如 AI 陪伴、代际关系、孤独感、轻社交、退休和养老想象、年轻人未来感等话题。
- 审稿指出“这段可能只是在作者自我感动”时。

调研问题至少包括：

1. 当下年轻读者缺什么：稳定陪伴、低压力社交、未来安全感、可持续生活、被需要感、具身体验或共同体归属。
2. 读者正在警惕什么：廉价鸡汤、完美 AI 伴侣、苦难消费、效率崇拜、伪乌托邦、说教式人文关怀。
3. 本章写的生产动作，能否落到一种现实情感需求上。
4. 本章写的老人 / Agent 关系，是否仍然指向人与人的重新连接，而不是用 Agent 替代关系。
5. 本章是否需要加入一个更贴近日常生活的触点，例如饭、天气、社区通知、低负担问候、线下活动或身体感。
6. 本章是否可以调动互联网行业共同记忆：需求评审、排期、上线、回滚、值班、工单、灰度、埋点、故障复盘、看板、版本号、最低验收、用户反馈等，并把它们转译成老人建设绿洲时的温柔反差。

调研来源要求：

- 优先使用近一年公开报告、问卷、平台讨论、书影音趋势、社交媒体观察和可信媒体报道。
- 至少交叉三类来源：研究 / 报告、媒体 / 访谈、读者或平台讨论。
- 不把单个平台热梗直接写进正文；热梗只能帮助理解情绪，不应成为作品口吻。
- 互联网行业梗要优先提炼成“共同工作经验”和“反差感”，不要直接照搬段子或平台黑话。
- 可复用已登记的素材库，例如 `internet-worker-hardship-meme-bank.md`；素材库只提供情绪来源和转译方向，不自动成为正文内容。
- 调研文字必须写回 `site/story/research/` 下的文件，并标明日期、问题、来源、结论和写作影响。

调研写回硬规则：

- 聊天里的调研摘要不算完成。来源列表、摘录性概括、判断依据、写作影响和不采纳项都必须落到文件。
- 短调研或跨章节调研写入 `site/story/research/research-notes.md`。
- 单章专项调研超过一个小节时，新建 `site/story/research/volume-XX-chapter-YY-research.md`，并在 `site/story/research/README.md` 登记。
- 正文、章节卡和审稿意见只引用调研结论，不承载完整调研正文。
- 如果调研结论影响 canon，应再同步到对应的 `background/`、`outline/`、`characters/`、`timeline/` 或 `chapter-cards/` 文件；不能只留在 `research/`。

调研输出格式：

```markdown
## YYYY-MM-DD 章节口味调研：[章节 / 节点]

### 调研问题

### 来源

### 发现

### 对本章的写作约束

### 不采纳项
```

### 1. 写前定位

先写一句本章任务句，格式如下：

`本章要让 [生产进展] 发生，同时让 [关系 / 承诺 / 共同体感] 前进一步。`

如果这句话只能写成设定解释，先不要写正文，回去补章节卡；如果它无法对应调研里的情感需求，先回去补调研。

### 2. 场景切分

每个场景只保留一个前台动作：

- 生产场景：采样、冷炉、退炉、打印、验收、维修、入口测试等只能选一个做前台。
- 情感场景：只保留一个可见动作，例如等一下、留一盏灯、改一句提示、保留一枚螺栓。
- 系统界面：每场最多突出一个主要界面，其他信息落到手、灯、停顿、物件、声音或一句人话里。

### 3. 人物使用

低戏份人物必须遵守“少量复用，不展示名单”：

- 一段里不要连续出现多个“姓名 + 功能动作”。
- 能用“下一班的人 / 记录者 / 验收老人 / 旁边调提示的老人”解决的，不强行点名。
- 已点名的低戏份人物应至少承担一点可记住的动作，比如改提示、贴标签、压字号、校版本，而不是只补岗位。
- 第二章及以后优先复用第一章已经露面的低戏份人物，除非新人物有明确情感落点。

### 4. Agent 边界

Agent 写作必须保持以下口径：

- 所有 Agent 初始都是通用标准本体，通过模块、工具或设施接口承担临时任务。
- Agent 可以建议、等待、提醒和执行，但不能成为全能管家或完美情绪伴侣。
- Agent 的小错误或过度工程化回答可以保留，让老人和 Agent 的关系有磨合。
- 每次 Agent 拒绝或排队，都要给出可理解的理由、下一次回应时间或可替代路径。

### 5. 互联网行业梗与反差感

本故事的第一批老人有大量互联网行业背景。正文应让读者隐约联想到熟悉的行业经验，但这些经验在绿洲里被重新使用：不再服务于压榨、内卷和甩锅，而是服务于等待、照看、修复和共同生活。

可使用的反差方向：

- 需求评审 -> 把“我不添乱”翻译成“需要安静陪伴入口”。
- 排期 / 里程碑 -> 不催进度，只写下一次回应时间。
- 上线 / 灰度 -> 不追求大规模发布，只让门口灯先亮一晚。
- 回滚 / 应急预案 -> 采样路线先确认撤回点，失败后先保住 Agent 身份链。
- 工单 / 值班 -> 不是追责单，而是等待理由和维护承诺。
- 版本号 / 验收 -> 不把“看起来能用”写成“已经修好”。
- 复盘 -> 保留异常曲线、退炉残片和旧臂螺栓，不包装成胜利素材。
- 用户反馈 -> 不是增长指标，而是“按下去以后人会不会以为自己掉线了”。

写法边界：

- 梗要让懂互联网行业的人会心一笑，不懂的人也能读懂现场动作。
- 每个场景最多放一个行业联想，不连续抛术语。
- 每章最多选择一个互联网痛点做温柔反转；若审稿认为轻梗数量已经足够，后续只做替换或减法，不继续追加。
- 可以写旧习惯被温柔改造，少写直接吐槽公司、老板、KPI 或职场苦难。
- 苦难素材只能提炼“读者为什么需要这种反转”，不能把老人写成现实职场苦难的复刻，也不能写真实公司、真实事故或真实组织标签。
- 反差感来自“同一套工具词被老人拿来照顾人”，不是来自夸张段子。
- 不要让互联网黑话替代人物声音。术语出现后，最好立刻落到一句人话或一个动作。
- 如果一句轻梗显得像作者点题，优先改成角色动作。例如不要停在“今天先不数人”，而是让宋清岚把人数栏收进第二层。

### 6. 技术词密度

工业线需要技术词，但不能写成状态流。执行以下规则：

- 一个小节里，`接入`、`维修`、`状态墙`、`账本`、`安静连线`、`标定` 等词只让一到两个成为前台。
- 连续两段都在写系统词时，下一段必须换成身体动作、物件状态或老人说话。
- 拒绝、失败、不能通过等信息不要只靠界面宣布，要让读者看见人怎么接住它。

### 7. 主题表达

主题只能从动作里长出来：

- 少写“不是……而是……”和“今天要证明……”。
- 少写“没有人鼓掌 / 没有音乐 / 没有欢呼”这类连续否定。
- 保留少数关键克制句，但其余用环境和动作替代，例如锁止件归位、低亮度、门口静一下、盒盖合上。
- “人文关怀”不直接喊出来，要具体成：不点名、保留位置、改提示、等下一轮、把失败痕迹留在门边。

### 8. 伏笔和物件链

重要物件必须有保管链：

- 第一次出现：说明谁看见、谁命名、保存在哪个层级。
- 中途转移：说明由谁登记、放入哪里、是否进入公共记录。
- 情感回收：说明它如何被大家看见，以及为什么不被包装成胜利。

第一章经验中的高价值物件链包括：灰边、异常曲线、退炉残片、旧臂螺栓、门口灯。

### 9. 首稿完成后的自查

首稿完成后先做本地自查，不急着进入下一章：

1. 结构：本章是否有生产进展，也有关系进展。
2. 调研：本章是否回应了调研中确认的真实情感需求，而不是只复述设定。
3. 行业反差：是否有一两个互联网行业共同记忆被温柔转译，而不是硬塞黑话。
4. 尺度：是否提前写满卷末娱乐设施胜利。
5. 人物：是否出现低戏份名单感。
6. 语言：是否用解释句替读者总结主题。
7. 世界观：是否误写成 Agent 独立反叛、公司控制、老人苦难或资源竞赛。
8. 连续性：关键物件、人物状态、Agent 限制和下一章钩子是否接得上。

### 10. 多方审稿

以下情况必须开多 subagent 审稿：

- 完成一整章草稿。
- 完成卷级关键节点，例如第一次事故、第一次维修、第一次娱乐设施试运营。
- 发生重大设定变更、人物功能边界变化或核心主题风险。

推荐审稿切片：

- `story_structure_editor`: 审章节弧线、危机升级、结尾尺度。
- `worldbuilding_agent_boundary_editor`: 审 Agent、OC、通信、模块、工业能力边界。
- `character_relationship_editor`: 审人物关系、低戏份名单感、老人-Agent 关系是否有磨合。
- `internet_culture_editor`: 审互联网行业梗、流程词和反差感是否自然，是否会心但不油滑。
- `style_language_editor`: 审小说感、技术词密度、口号化和 AI 味。
- `continuity_editor`: 审 `CH-*`、`TL-*`、`CHAR-*`、物件链和下一章衔接。

整章定稿前，推荐至少做一次五方最终审稿：

- `story_structure_editor`: 确认章节弧线、结尾尺度和下一章承接。
- `human_care_theme_editor`: 确认人文关怀、纯粹情义、禁忌方向和苦难素材边界。
- `world_agent_boundary_editor`: 确认 Agent 通用本体、模块接口、OC / 绿洲币成本和工业 V1 边界。
- `internet_culture_taste_editor`: 确认互联网行业梗、娱乐传播点和年轻读者口味。
- `style_continuity_editor`: 确认语言风格、人物密度、意象连续性和伏笔链。

subagent 默认只读，不直接改正文。每个审稿切片必须返回：

- `ready / not ready` 判断。
- P0 / P1 / P2 问题分级。
- 涉及文件和位置。
- 必修项与可带入后续章节的提醒。
- 是否建议继续加梗、替换、减法或停止修改。

审稿结果必须写回 `site/story/reviews/editorial-notes.md`。

### 11. 最小补丁

审稿后优先做最小补丁，不轻易重写整章：

- P0：设定、结构或价值方向错误，必须先停下修。
- P1：影响进入下一章的问题，做最小正文补丁后快速复审。
- P2：可记录但不阻断，进入下一章时主动规避。

最小补丁优先顺序：

1. 修 canon 漂移和禁区误触。
2. 修调研错配：读者需求、社会口味和正文动作对不上时，先调整场景承载方式。
3. 修行业梗错位：黑话太硬、段子太满或反差感没有落到人物动作时，先转译成生活动作。
4. 修人物功能边界和低戏份名单感。
5. 修解释性主题句。
6. 修术语密度。
7. 修物件链缺口。

最终极小润色只在多方最终审稿后执行，且必须更克制：

- 只处理重复出现的 P2 或作者自己能明确说明的单点修辞风险。
- 每轮最多改一处，或一组同类极小措辞。
- 优先把判断句、点题句和热词句改成角色动作。
- 不新增剧情、不新增人物、不扩大设施尺度、不追加新梗。
- 改完更新正文版本号，例如 `v0.8.1`，并把采纳原因写回 `editorial-notes.md`。

### 12. 通过标准

一章可以进入下一章试写，需要满足：

- 无 P0 / P1 阻断。
- 调研正文和结论已经写回 `site/story/research/`，且正文没有违背本章调研约束。
- 如使用素材库，正文只转译情绪和反差，没有让现实热词、真实苦难或平台段子直接进入小说口吻。
- 至少有少量行业经验反差，但没有写成互联网黑话展示。
- 如果已完成最终多方审稿，所有切片均为 `ready`，或已记录不采纳理由；重复 P2 已经极小补丁或明确带入下一章规避。
- 本章情感胜利清楚，但没有提前消耗卷末胜利。
- 下一章钩子是动作钩子，不是主题口号。
- 审稿记录已经写回。
- 验证命令通过。

### 13. 卷级审阅与最小优化

完成一卷后，例如第一卷 `CH-001` 到 `CH-036`，必须先做卷级审阅，再决定是否进入下一卷或下一章。卷级审阅不是重写流程，默认只读，先产出报告；除 P0 / P1 或重复出现、已影响阅读的 P2 外，不做大改。

卷级基线冻结：

- 先列明本轮审阅对象的正文版本、调研文件、章节卡、README 登记和审稿记录。
- 冻结后不要边审边改。审阅期内只允许记录发现，所有正文修改必须等综合结论形成后，以最小补丁方式执行。
- 若发现某章版本号、README、章节卡或审稿记录不一致，先记为 canon / doc sync 问题，不直接把其中一个文件当成最终真值。

输入材料：

- 本卷所有正文草稿，例如 `site/story/draft/volume-01-chapter-001.md` 到 `volume-01-chapter-004.md`。
- 本卷所有章节卡、调研文件、`site/story/draft/README.md`、`site/story/research/README.md` 和 `site/story/reviews/editorial-notes.md`。
- 与本卷相关的 `background/`、`outline/`、`characters/`、`timeline/` 文件。
- 章节级审稿结果、最小补丁采纳记录、最终验证证据和仍需带入后续章节的 P2。

推荐卷级审阅切片：

- `story_structure_editor`: 审整卷起承转合、章节推进、卷末尺度和下一卷钩子。
- `human_care_theme_editor`: 审照护伦理、低压力参与、退出 / 旁听 / 不在线权利，以及是否滑向苦难消费或情感债。
- `world_agent_boundary_editor`: 审 Agent 通用本体、模块接口、OC / 绿洲币成本、工业线成熟度和剧场开放尺度。
- `internet_culture_taste_editor`: 审互联网行业共同记忆是否自然转译，是否出现黑话堆叠、项目复盘感、营销口号或硬梗。
- `style_continuity_editor`: 审中文质感、技术词密度、章间意象连续、人物名单感和解释性主题句。
- `continuity_canon_sync_editor`: 审正文、章节卡、调研、README、editorial notes、timeline、characters 是否同步，尤其关注旧种子句是否会把已修问题带回来。

卷级检查维度至少包括：

1. 主弧线是否顺畅：生产进展和关系进展是否逐章递进，而不是每章重复同一种安静胜利。
2. 情感尺度是否稳：卷末有余味，但没有写成盛大开幕、稳定量产、完整工业自给或一次性治愈。
3. 人物连续性是否成立：核心人物的能力、承诺、退让和关系状态是否与前章一致。
4. Agent 和世界边界是否一致：Agent 不能越过工具 / 模块 / 接口限制，工业线不能提前成熟。
5. 互联网痛点转译是否自然：读者能感到反差，但正文不像项目汇报、发布会文案或社交平台段子。
6. 物件链是否闭合：灯、扶手、维修床、系留扣、旧螺栓、短节目单等是否有保管、转移和情感回收。
7. 文档真值是否同步：章节卡、调研、正文、README、editorial notes 和时间线没有互相打架。

卷级问题分级：

- P0：价值方向、世界边界、主弧线或 canon 出现根本错误，不能进入下一卷。
- P1：影响本卷作为稳定基线的问题，必须做最小补丁并快速复审，例如能力越界、卷末过度胜利、章间矛盾、旧章卡会反向污染正文。
- P2：不阻断稳定基线，但应记录并在下一卷规避；若同类 P2 跨多章重复，升级为卷级最小优化候选。

最小补丁原则：

- 正文优化必须最小、可追溯，并写明对应审稿发现。
- 不新增剧情、不新增人物、不新增能力、不新增互联网梗。
- 优先删减、收窄、换成动作或物件承载；不把卷级审阅变成整章重写。
- 只修 P0 / P1，以及重复 P2 中已经形成阅读噪音的同类问题。
- 改完必须同步正文版本号、README 登记、章节卡旧种子句、调研引用和 `editorial-notes.md` 采纳记录。
