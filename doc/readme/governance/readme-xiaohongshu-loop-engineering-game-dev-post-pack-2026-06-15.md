## 使用说明
- 这篇是项目实践分享，不是概念科普，也不是对外发布承诺。

- 开头必须先给陌生读者一个入口：`oasis7` 是一个仍在推进中的长期游戏项目，开发方式是“人类开发者 + 一群 agent 队友”。
- 叙事逻辑必须是：先有项目里的 harness / 多线程接力实践，再看到 `Loop Engineering` 这个词并发现它和当前项目高度契合，最后才分享落地经验。
- 少用内部治理词。正文里尽量把 `task/worktree` 解释成“每个需求都有自己的工作现场”，把 `role slice` 解释成“让不同角色只判断自己该判断的部分”。
- 对外只讲可公开的 workflow practice：
  - task/worktree 任务入口
  - owner / role slice 分工
  - execution log / verification evidence
  - 玩家、测试、评论、PR 反馈回流
- 不展开内部权限、CI/admin merge、具体 subagent runtime、未公开 roadmap、task UID、PR 链路或故障细节。
- 不要承诺：
  - `全自动闭环`
  - `不会漏问题`
  - `上线零事故`
  - `社区反馈一定进入版本计划`
  - `单个 AI / Agent 独立完成完整游戏开发`

## 正文建议
```text
如果你第一次刷到这个项目，先简单说一下背景。

oasis7 是我这段时间一直在做的一个游戏项目。更准确一点说，是我作为人类开发者，和一群 agent 队友一起推进的。

在做这个游戏的过程中，我自己先搭了一些 harness。

说人话一点，就是一套多线程、多 agent 接力系统：前一个 agent 做完一段，留下足够的上下文、证据和下一步，后一个 agent 能接着往下做，而不是每次都从头解释一遍。

一开始我没给它起什么名字，只是觉得游戏项目太长了，不能靠一次聊天、一次生成、一次灵感往前推。

尤其是多个 agent 一起做事的时候，真正麻烦的不是“让它们干活”，而是让它们接得住彼此的工作。

前几天刚好看到别人提到 Loop Engineering，我突然发现，这个词和我在项目里做的事情非常契合。

它不是写一个更厉害的 prompt，也不是让 agent 一路自动跑到底，而是把“提出需求、拆开问题、做出改动、验证结果、接住反馈”设计成一个能回来的环。

说白了，每件事都要知道从哪里开始，由谁判断，怎么确认，做完以后又回到哪里。

在当前项目里，我踩出来的第一个经验是：需求不能只停在聊天里。

游戏开发里，一个想法很容易从“我们要不要试试这个”开始，然后散在聊天、文件、临时备注和脑子里。短期看没问题，长期看，这就是断线的开始。

所以现在我会尽量让每个需求都有自己的工作现场：谁负责推进，做到什么算完成，过程中看了什么、改了什么、卡在哪里，都要留下记录。

这听起来有点笨，但它救过很多次场。

第二个经验是，不要让一个 agent 什么都判断。

游戏项目里的问题很杂。有时候是在问玩法是不是成立，有时候是在问画面和交互是不是对，有时候是在问 runtime、viewer、QA，还有时候只是要判断一段对外说法会不会让玩家误解。

这些问题如果都丢给一个“万能助手”，它很容易答得很完整，但不一定答在责任边界里。

所以我现在更习惯把工作拆给不同角色。协调的人只负责把事情串起来，玩法、画面、验证、对外表达，尽量让真正负责那一块的角色来判断。

这点对游戏开发尤其重要，因为“能做出来”和“体验成立”，经常不是同一个问题。

第三个经验是，完成不能只靠感觉。

每一步都要尽量留下证据：看过哪些材料，跑过什么验证，结果是通过、失败，还是只是暂时看不出问题。

尤其在游戏项目里，“能启动”和“真的可玩”，“画面出现”和“体验成立”，中间差很多层。

如果没有证据，团队很容易在“应该好了吧”里面继续往前走，然后下次再遇到同一个坑。

第四个经验是，反馈不能停在当下。

玩家反馈、测试问题、PR 评论、线上观察，都不是某次沟通的结尾。它们要能回到下一轮任务里，要么变成验证项，要么变成设计调整，要么至少变成一个明确的“不做，但为什么不做”。

这是我现在觉得 Loop Engineering 最有价值的地方。

它不是让项目看起来更高级。它更像是在帮一个长期项目少一点“做着做着就忘了为什么”的时刻。

AI 让单次执行变快了，但也会带来一种新的错觉：看似推进很多，其实项目状态越来越散。

所以我现在反而没那么迷信“全自动”。人还是要负责目标、取舍和最后的结果。

在游戏开发里，先让每个环节可追踪、可验证、能回头，比一上来追求自动跑完整条链路更重要。

至少对 oasis7 来说，这是目前比较实用的一种落地方式。

如果你也在做游戏或长期项目，你们最容易断掉的是哪一环：需求、实现、验证，还是反馈？
```
