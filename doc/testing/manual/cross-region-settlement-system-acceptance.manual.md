<a id="cr-verify-001"></a>
## CR-VERIFY-001：分层与物理接收

建立供给 10 单位的合同，分别运行陈旧报价、确认前资源漂移、有效出发、途中损失 2、到达但容量不足、容量足够接收、接收后里程碑仍待决。每步查询相同权威快照的库存、货物、保管、所有权与支付。漂移拒绝零资源变化；到达无接收与最终收益；确认损耗保留 8 单位可追踪货物。部分交付只在政策允许且数量区间不重叠时可结算；整批政策不能通过拆请求绕过。并发接收争抢容量不得双占或二次入库。最终所有权与收益仅在对应条件提交后生效。

<a id="cr-verify-002"></a>
## CR-VERIFY-002：原子提交与单次结算

同一义务分别注入相同请求重复、身份相同内容不同、不同请求身份、并发到达/释放、合同 revision 更新和历史 receipt 重放。在提交前、写入中、提交后响应前注入故障并恢复。断言失败无部分货物/资金/所有权/需求变化；成功仅一个 effect，响应丢失返回原 receipt，新身份不再履行已完成义务。总锁定/释放/退款/费用及货物/损耗守恒，版税/奖励/需求履行不重复。将任何子账本写入失败作为反例，不能仅验证函数返回值。

<a id="cr-verify-003"></a>
## CR-VERIFY-003：争议、取消与恢复

分别令争议在结算前后进入权威序列；校验只阻断受争议未结算义务，合法已结算历史保持。证据窗口到期但无有效裁决时不得自动付款。运行拒收后的等待、授权改道、退回、重谈、取消、损失赔偿及无合法路线安全停止；检查仅释放未消费且无剩余义务的占用，退回未入库前不恢复可用库存。checkpoint/replay 必须保留裁决、剩余量、资金和义务 lineage；重谈/补偿不能重复原收益或凭空生钱。缺依赖/损坏日志时阻断相关执行并保留证据；其他合同继续。

<a id="cr-verify-004"></a>
## CR-VERIFY-004：读面、隔离与资源上限

以同候选同权威快照比较 Viewer、pure API 与 Agent 的物流、保管、所有权、资金/争议、blocker 与下一步。真实外部浏览器覆盖桌面与窄屏；断连、stale、未知 authority、隐私限制不得显示成功或泄露私有证据，重连后查询原结果而非自动再次结算。超过预先声明的证据/路线/里程碑上限、超时和落后节点均明确拒绝/阻断，无部分 effect，也不冻结无关交易。另在固定规模/硬件/并发与窗口下记录延迟分位数和内存，阈值须先由 owner 冻结；未定量时不宣称容量达标。
