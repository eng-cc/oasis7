## 一、产品定位与目标

客户端服务 oasis7 项目负责人的个人开发工作，提供 macOS 优先的独立桌面入口。打开项目后，用户能够回答：当前最重要的目标是什么，已经验证到哪里，今天的工作依据哪些决定，哪些问题确实需要自己处理。

| 原始问题 | 产品应提供的结果 | 观察方式 |
| --- | --- | --- |
| 短期与长期目标分散，进度难判断 | 从当前阶段沿里程碑、工作和验收依据下钻，也能回到长期方向 | 用户能说明下一项交付、已知进展及未知范围，并打开依据 |
| 制定规范后忘记理由，决策难连续 | 可检索当前适用规则，查看理由、范围、历史后继和尚未同步的决定 | 用户能找到当时决定和现在适用条款，分清规范与实现状态 |
| Codex 会话、分支和任务切换繁琐 | 在工作目的旁查看真实执行状态，并向正确环境和会话发送明确动作 | 用户能定位等待输入或失败的工作，操作结果有回执或不确定说明 |

工程工具保持在 engineering 文档域，不增加游戏产品第五域。游戏内 Agent、玩家 Viewer 与开发 Codex 会话分别建模。

首版不承担完整 IDE、通用多租户管理平台、跨机器安装平台或自主 Agent 调度器的职责。它关联现有目标、规范和交付事实，保留必要的个人记忆；任务本身仍可只存在于 PR、已有 Issue 或受支持开发会话中。

## 二、用户与使用场景

主要用户是同时承担产品决策、实现与交付的项目负责人。用户可能并行使用本地工作树、多个 Codex 会话和个人云端开发机，已有有效授权与项目操作习惯。

| 场景 | 用户问题 | 本次操作的完成标志 |
| --- | --- | --- |
| 开始一天的开发 | 今天最应推进什么，昨天有什么变化？ | 看见当前重点、已核实交付、真实阻塞和来源变化 |
| 准备作出决定 | 之前为什么这么定，这次会影响什么？ | 找到适用条款及理由，能区分历史决定、草稿和待同步内容 |
| 多项开发并行 | 哪个会话在做什么，哪些在等我？ | 工作目的、环境、会话与 PR 清楚关联，可进入正确处理入口 |
| 中途离开与恢复 | 关窗口会发生什么，重新打开还能续上吗？ | 能预期运行行为，恢复已有信息，不重复执行已发出的动作 |

次要使用者是按用户明确指令开发或刷新看板的 Codex。Skill 提供调用方法与按需参考，不构成实时后台服务，也不拥有产品规则的另一份副本。

## 三、信息架构与用户旅程

### 四个主视图

| 视图 | 首屏重点 | 详情与主要入口 |
| --- | --- | --- |
| 方向与进度 | 当前阶段、近期交付、已验证结果、阻塞 | 长期方向、里程碑依赖、关联工作、验收条款和证据 |
| 规范与决策 | 当前适用规则、需要关注的变化、尚未同步的决定 | 原文、适用范围、理由、历史后继、冲突及受影响工作 |
| 开发执行 | 工作目的、环境、分支与工作树、PR/CI、会话活动 | 会话详情、受支持的继续/输入/中断、交付来源 |
| 待我处理 | 真实输入请求、阻塞性问题、待选择事项 | 必要背景、选项影响、推荐理由、处理入口及回执 |

项目与环境选择、来源连接状态、搜索和最近成功读取时间属于共享入口。视图之间共享关联，打开 PR 或条款时保留当前筛选和返回位置。

### 典型旅程

1. **首次打开**：启动 App，选择本地 oasis7 仓库；先看到可读取的规范、目标和 Git 信息，再按需连接 GitHub 与 Codex。可选连接缺失时，已可用区域继续工作。
2. **确定下一步**：从当前阶段进入里程碑，查看完成条件、已核实证据和相关工作；需要执行时，明确选择目标范围及环境，再发起开发动作。
3. **回顾并修改决定**：搜索规则，打开当前条款和历史理由；记录新的明确决定或草稿，看到受影响工作；规范回写及实现同步分别有可核实结果。
4. **处理运行请求**：从待我处理进入具体会话请求，核对工作背景并回答；返回开发执行查看实际回执。重复打开或恢复连接不会重复发送答案。
5. **离开并恢复**：关闭窗口后从菜单栏重新打开；完整退出先明确自管活跃工作的处理方式；异常退出后展示最近已知事实和未决结果，核对后继续。

## 四、产品需求

<a id="REQ-CC-001"></a>

### REQ-CC-001：独立入口与项目上下文

日常交付为可直接启动的 macOS App。用户无需先开终端、启动看板服务或部署中心服务；浏览器界面用于开发预览。

打开项目时识别实际仓库与工作树，显示当前项目、环境、分支和读取基线；允许切换已有项目上下文。未提交文档与已提交版本可辨认，工作树内容不能标为 main 已生效内容。

恢复上次项目时同时恢复视图偏好和阅读位置。路径不存在或仓库不匹配时，说明具体问题并允许重新选择；不静默改成另一个目录或仓库。

<a id="REQ-CC-002"></a>

### REQ-CC-002：来源可信与局部可用

每项重要结论能够打开来源，显示可取得的源版本、观测时间、性质和覆盖范围。性质至少区分源事实、Agent 汇报、模型归纳和待核实关联；未知字段不补造。

各来源分别展示加载、成功空结果、部分读取、过期、错误和未接入。读取失败保留最近成功事实，说明哪个区域受影响；GitHub 不可用不妨碍阅读已加载规范，Codex 未连接不阻塞其他视图。

刷新读取既有事实或订阅已支持事件，不暗含模型运行、Git fetch、分支切换或远端写入。需要分析或执行的动作另有明确入口，沿用实际授权。

<a id="REQ-CC-003"></a>

### REQ-CC-003：短期与长期目标及进度

首页先呈现当前阶段与近期交付，长期方向保持可见且层级独立。当前阶段读取 core PRD 的“当前阶段交付目标与全局 P0”及其主责引用，不采用文件开头历史里程碑作默认。沿“长期目标—里程碑—关联工作—验收依据”下钻；工程支撑工作可独立筛选，沿用项目既有产品分类。

目标、阶段和依赖来自当前主责文档或用户明确确认的关系。一个工作可关联多个目标；未确认关系显示为建议，不自动成为依赖或阻塞，不把长期愿景的全部内容提升为当前前置条件。

明确列出完成条件、已核实部分、尚未覆盖或未知部分。只有适用验收集合、分母与结果均可核实时，展示“已验证项 / 适用项”；其他情况使用文字说明，不生成总体完成率。

<a id="REQ-CC-004"></a>

### REQ-CC-004：规范与决定的连续性

按事项范围展示当前规则摘要、主责条款、理由、源版本和后继关系，支持中文、标题、路径与条款 ID 搜索。历史工作可以打开当时依据，也能找到现行条款。

规范效力依据主责身份和显式替代关系；修改时间、被引用次数和模型记忆不能单独决定优先级。无法消解的冲突列出来源及受影响结论，不让无关工作一并阻塞。

用户可以保存决定草稿、记录明确的新决定及其理由、范围、与旧条款的关系。草稿、用户已决定、正式规范已更新、实现已同步分别显示；保存草稿不改变正式规范。

首版通过原文编辑入口或明确的 Codex 工作完成回写。只在已授权且有实际结果时更新规范状态；未找到正式承载位置时呈现具体缺口，不新建通用决策登记系统。

只有保存了真实阅读版本且能核实变更时，展示“自上次查看的变化”。用户手工关联、阅读位置、决定草稿，以及用户已确认但尚未回写正式规范的决定，在重启与缓存重建后保留；决定内容、理由、范围及真实确认信息一并保存。

<a id="REQ-CC-005"></a>

### REQ-CC-005：围绕工作目的组织开发执行

执行列表以工作目的和服务目标为主，展示环境、分支/工作树、最近活动、当前结果及下一步。PR、适用 CI 与会话运行状态并排保留，不合成为虚构的统一完成状态。

仅有 PR、尚无 Issue 的工作能正常展示；尚未产生 PR 的明确开发会话可作为执行入口，不要求补建 Issue 或客户端任务记录。已有关联可复用；建议关联等待核实。

同一分支上的多个会话分别呈现，同一持久会话的多个运行实例保留各自可观察状态。来源提供子 Agent 信息时可以展开，其身份与项目目标、游戏 Agent 保持区分。

历史可读取范围与实时可观察范围在会话详情中清楚可见。一个新连接不能声称已接管其他 App、CLI、IDE 或云端的全部任务。

<a id="REQ-CC-006"></a>

### REQ-CC-006：待我处理聚合真正需要用户介入的问题

待处理条目回答：具体需要决定或输入什么、为什么现在需要、选项及影响、建议理由、受影响工作和处理入口。普通提醒与真实阻塞可区分，不将全部待办列为待批准。

相同问题可引用多项受影响工作，避免重复打断；运行时输入请求保持独立真实身份，不能把不同会话的问题错误合并。已处理条目保留结果入口，重复刷新不重新成为未处理。

已有授权范围内的普通实现、测试和修复继续执行。只有实际运行时请求、真实权限/输入缺口或需要用户选择的事项进入相应处理流程。

<a id="REQ-CC-007"></a>

### REQ-CC-007：明确目标和能力后执行

每个连接独立说明可读取、可订阅、可控制及覆盖范围。动作只在真实支持时提供；不可用时显示原因，读取历史不自动获得控制能力。

用户可从目标或工作详情发起任务，在发送前看见工作范围、依据版本及执行环境；继续、追加输入、回复运行时请求和中断均指向实际会话与运行目标。已有明确授权不重复索取。

运行请求返回后，按真实回执及状态更新展示。按钮点击只表示用户发起操作意图；是否已发送及执行结果按实际发送记录、回执和来源状态展示，客户端不得修改本地缓存来宣称远端任务、PR、规范或部署已经改变。

<a id="REQ-CC-008"></a>

### REQ-CC-008：不确定结果与恢复

操作超时或连接中断时，区分“尚未确认结果”和“来源已确认失败”。结果未知的启动、追加输入或写入不自动重发；先核对已有结果，再提供可理解的处理入口。

取消订阅与中断工作是不同动作。断线只能说明观察中断，不能把会话改为空闲、失败或完成；中断请求被接受也不等于任务已经停止。

重新打开 App 或恢复连接时保留未决操作及原目标，先恢复可用事实；不能仅凭相同分支或会话名称把控制移到另一个运行实例。

<a id="REQ-CC-009"></a>

### REQ-CC-009：窗口与执行生命周期

关闭主窗口后 App 留在菜单栏，自管工作继续；用户可以从菜单栏恢复主窗口。普通窗口关闭、视图切换和断开观察不发送停止指令。

完整退出且确认没有活跃自管工作时，保存个人数据并结束空闲自管服务。仍有活跃或无法确认状态的自管工作时，提供留在后台、等待结束后退出、明确停止后退出；默认不停止。

活跃范围包含生成、等待输入或批准，以及来源能够核实的后台工作。停止失败或结果未知时不能宣称已结束。退出客户端不停止外部运行时拥有的工作。

首版不保证自管任务跨 App 完整退出、崩溃、强退或系统重启继续。重新打开时按 [REQ-CC-008](#REQ-CC-008) 恢复，不自动重跑；更新重启也遵循同一退出行为。

<a id="REQ-CC-010"></a>

### REQ-CC-010：中文与高密度信息交互

页面优先使用紧凑列表、表格、按需展开详情和来源跳转。支持键盘导航、可见焦点、明确标签与读屏；状态同时使用文字，不仅以红绿颜色区分。

中文短查询如“规范”“合入”可以找到适用内容。中文组合输入期间的 Enter 不误触搜索提交或发送指令；搜索、筛选和长列表滚动不丢失当前编辑内容。

长日志和大量结果按需加载，提示已显示范围和缺失片段，允许停止阅读流而不停止工作。代表性数据下的响应和系统体验需要真实 macOS 验证，未测量前不宣称具体性能。

<a id="REQ-CC-011"></a>

### REQ-CC-011：个人数据与隐私可预期

来源缓存、个人持久数据和未决操作分别管理。重建索引或清理可重建缓存不删除手工关联、阅读位置、决定草稿、已确认但尚未回写的决定或尚未核实的操作。

用户能够查看当前连接账号、环境和读取范围。新增长期凭据使用系统凭据存储，不写入项目、前端资源或普通诊断日志；存储失败时说明会话内使用等实际能力，不默默降级为明文保存。

默认保留使用所需摘要与来源，不默认记录完整提示词或对话原文，不自动把本地内容上传至自建云端。文档、PR 内容和日志作为待展示内容处理，不因其中的文字执行本机命令。

<a id="REQ-CC-012"></a>

### REQ-CC-012：渐进接入与首版边界

先贯通本地文档和 Git，再接入 GitHub 的 PR/CI/评审及受支持的本地 Codex。Issue/Project 和个人云端环境按需接入，缺少它们不妨碍本地使用。

云端与本地保留独立环境和能力说明；同一项目、分支或会话标题不能隐去环境差异。首版不承诺自动发现、接管全机或全部远端任务，也不自动安装或公开暴露远端运行服务。

技术基线为系统设计选定的 Rust 核心和桌面客户端形态。实现范围以本 PRD 的用户承诺为准，不因存在可用框架而加入第二套界面、公共网站、通用平台或额外任务审批。

<a id="cc-product-states"></a>

## 五、状态与进度的解释

| 来源或状态 | 可以说明 | 仍须单独核实 |
| --- | --- | --- |
| 文档为 active | 对应文档身份及条款效力 | 能力是否已实现、是否通过验收 |
| 用户已作出决定 | 本次明确意图及授权范围 | 正式条款是否更新、实现是否同步 |
| PR 已合入 | 对应代码已进入目标分支 | 部署、整体体验及目标验收 |
| 某次 CI 通过 | 适用测试对相应版本的结果 | 其他版本、未覆盖环境与验收条件 |
| 会话一轮结束 | 该运行来源报告本轮结束 | 其他后台工作、CI、PR 或项目目标完成 |
| 查询失败或连接中断 | 本次读取或观察不可用 | 没有任务、没有阻塞、运行已停止 |
| 有完整适用验收集合 | 可以呈现已验证项与适用项 | 未核实项是否通过、其他目标进度 |

来源标识、观测时间和适用范围跟随结论展示。最新源 HEAD、实际测试版本和 main 前进分别解释，沿用现行开发流程，不从一次 main 变化推导全部既有 CI 失效。

## 六、验收条件

下表是客户端功能的产品验收，不为每次文档或一般开发任务增加完整运行要求。实现时按改动覆盖对应条件，系统设计映射可自动化、连接器回放与真实桌面验证。

| 稳定条款 | 对应需求 | 场景与通过条件 |

## 七、首版范围与后续扩展

首版按三个可用增量实现，递进关系用于明确用户能获得什么，不创建新的仓库任务状态机或固定审批环节。

| 增量 | 用户可用结果 | 尚未覆盖范围 |
| --- | --- | --- |
| 桌面基础 | 安装启动、打开真实项目、规范/Git 阅读、中文搜索、来源定位与个人位置恢复 | GitHub 和会话区域可明确未连接 |
| 四视图闭环 | 目标关联、PR/CI、规范理由与历史、待处理问题、局部离线和覆盖解释 | 尚不提供未接入运行时的控制 |
| 开发执行闭环 | 支持版本的本地 Codex、真实输入请求、继续/中断、未知结果恢复和退出协调 | 外部会话及远端按实际能力提供，不宣称全量接管 |

个人云端接入、自动更新和其他桌面系统由实际使用需求决定。若明确要求完整退出后任务继续、多个客户端共享执行现场或重启后无人值守恢复，再扩展独立执行宿主；其新承诺须同步到产品与系统设计。

首版不以包体、内存或帧率的未测量数字作为成效声明。评估产品价值时，以前述用户问题能否依靠真实来源完成为主，并记录代表性场景下实际观察到的检索与操作体验。
