# 开发流程规范

本文定义 oasis7 日常开发、验证、评审、合入和交付的通用规则。目标是让修改容易完成、结果可以核实，并把保护措施放在实际需要它们的操作边界。

## 1. 适用范围与规则边界

本文是通用开发流程的唯一规范。脚本、CI、AGENTS 和 skills 负责执行或说明这些规则，不得另设任务准入、审批、状态、证据材料或完成条件。发现不一致时，应修正对应实现和入口，不得用额外证明补偿规则冲突。

每项工作有一个明确负责人。负责人可以是人或主 Agent，可直接分析、设计、实现、自测和组织评审；专业角色和 subagent 按任务需要使用，不构成所有修改的必经环节。

Git、PR、实际 CI 结果和评审记录承载代码交付事实。Issue 和 Project 按跟踪需要使用；普通修改可以只有 PR。本地开发、测试和 PR 验证不依赖 Project 可用性，不要求额外任务标识或工作区登记。

按用户选择的工作类型交付：分析和方案请求交付结论或方案；实施授权覆盖同一目标和范围内的修改、测试及修复。提交更新、测试失败或 main 前进不要求重复确认。扩大目标或范围、增加尚未授权的外部影响、改变交付对象时，才确认新增部分；已经明确授权的动作不重复申请。

修改必需检查或合入策略时，必须同步规范、实现、执行入口和适用的 GitHub 保护设置，并核实它们一致。当前生效的保护规则始终约束实际合入；只修改文档不能解除已有强制检查或代替设置变更。

## 2. 日常开发

开始时明确问题、预期结果、必要的范围边界和验收方式。简单修改写在 PR 描述即可；复杂设计使用已有设计文档。只读查询和分析无需创建流程任务、分支、工作区或远程证据评论。

代码修改在独立分支进行，不直接修改 main。需要并行隔离时使用 worktree；工作区路径不是开发许可。保留用户已有改动，不擅自覆盖他人工作，并遵守明确的只读目录和资源边界。

一个 PR 围绕一个清楚的交付目的，可以同时修改多个 crate、测试、配置和相关文档。原子修复不按包数量强行拆分；确有独立目的或独立交付价值时再拆 PR。

负责人可连续完成复现、实现和局部验证，无需逐步发布计划字段或等待机械状态转换。可稳定自动复现的行为缺陷，应有能检出该缺陷的回归测试；已有测试能够检出时直接复用，覆盖不足时增加或修正。机械修改不强制增加与实现重复的测试。

采用 subagent 时，说明具体问题、必要上下文、允许的写入范围和期望结果。并行编辑应避免重叠，由负责人合并结果；不要求固定角色组合、模型证明、派工回执或额外评审文件链。

修改影响对外行为、接口、部署方式或使用方法时，同步维护相关文档。文档长度是编辑参考，不能作为是否允许提交的门禁，也不能通过压成长行掩盖过量内容。

## 3. 验证与评审

先用最小有效验证获得反馈，再由 CI 执行完整的必要检查。具体命令和环境准备见 [testing-manual.md](../../../testing-manual.md)。验证记录应能说明执行了什么、针对哪个版本、结果如何及未覆盖的部分，不另造通用放行回执。

CI 按实际改动及受影响消费者选择测试。选择范围必须考虑新增、删除、重命名两端、依赖关系、features、生成输入、共享配置及锁文件变化；无法可靠判断时扩大覆盖。包关系用于选择测试，不用于禁止合理修改。

最终 required check 必须在所有选中的必要任务结束后汇总，并以 `always` 等可靠机制在失败或取消路径仍执行。只有预期任务全部真实成功才能通过；失败、取消、缺失、未知结果，或应执行却跳过的任务均不得算成功。未被计划选中的任务可以不执行。

CI 结果必须对应实际 source HEAD 和测试对象。测试合并树时还应能识别真实 base、event commit 和 tested tree；不得把只测试过源分支的结果宣称为最新 main 组合验证，也不得将旧结果改写成新版本证据。

普通 PR CI 的 GitHub 权限只读，不授予生产凭据或部署身份。需要特殊权限的验证使用受控入口，固定已批准的待测版本并授予最小权限。PR 缓存和产物不得直接成为特权入口的可执行输入。

改变 CI workflow、测试入口或选择规则的 PR，必须接受独立评审，并验证测试确实按既定保护要求执行。候选代码不能通过删减必要任务、改变汇总条件或伪造同名成功状态为自己放行。

评审按复杂度和风险选择。普通变更由负责人自检并按需安排独立评审；机械文档不强制领域角色或 QA。权限、凭据、共识、持久化兼容、不可逆迁移、关键安全边界和开发门禁变更必须有对应能力的独立评审，评审者不得批准自己编写的部分。

评审记录说明所审阅的版本、结论、阻断问题及处置即可。真实的正确性、安全性或数据丢失风险必须修复或以事实证明不适用；非阻断建议可以说明理由后不改，不自动创建后续任务。修改后的复审针对实际变化及受影响部分，不强制所有角色重复全量审阅。

CI 和独立评审可以并行，合入时汇总两者。启用 GitHub 原生合入前分支必须跟上 base 的保护，验证实际合并组合。源代码更新后，重新验证受影响内容；无关的 main 前进本身不要求重做设计、开发或全部评审。需要更新分支时满足原生保护，并重新执行必要的普通 CI；不能承诺不同 base 永远无需重测。

普通 CI 是默认验证方式。缺测试先补 CI；只有明确需要普通 CI 难以提供的环境、跨系统状态或部署恢复过程时，才增加专项集成验证。专项验证必须说明具体环境缺口、验证目标、执行版本、实际结果和剩余限制。高风险本身不等于需要重复执行另一套相同 CI。

已有绿色结果后追加阻塞验证时，先暂停合入并触发包含该项的 PR 验证；当前版本通过后才解除相应暂停。删除标签或修改描述不能自动取消尚未满足的验证要求。

## 4. PR 与合入

PR 标题和完整 commit message 使用英文。

PR 描述具体问题、主要改动、验证结果和重要风险，按需链接 Issue。可以提前创建草稿获取反馈，也可以在完成实现后创建；草稿不是强制生命周期阶段。已有同一目的的 PR 应继续更新，不因修复或重新验证创建重复 PR。

用户要求暂停合入、发布或部署时，将限制记录在对应 PR 或操作入口可见的位置，并确保自动执行路径遵守。限制绑定实际动作，不阻止无冲突的开发和测试；只有来自用户或已授权主体的后续指令才能解除。

合入前检查当前 PR 和 source HEAD、全部必需检查、适用评审及阻断问题、冲突、权限和用户限制。必要检查未成功、真实阻断问题未解决、身份不明确或存在有效暂停指令时，不得合入。

默认使用正常受保护的合入路径，不以 `--admin`、关闭保护或伪造成功绕过门禁。确需调整规则或执行管理员操作时，应已有覆盖该动作的明确授权；管理员权限不代替真实验证和必要评审。

合入操作必须绑定已检查的预期 source HEAD，防止新 push 在检查后替换候选内容。源版本变化后重新检查受影响的验证和评审。自动合入仅在实际配置支持且其保护条件满足时使用，不假设存在 merge queue 或已启用 auto-merge。

## 5. 交付、状态与清理

代码任务在验收满足且实际 PR 已合入后完成代码交付。确认真实 merge 状态和对应提交，向用户报告结果及重要限制；不要求另建准备完成、任务完成和终态完成的证明链。

若用户目标还包含部署、数据迁移、真实环境验收、多个 PR 的整体结果或其他明确义务，继续完成这些工作后才能宣称整个请求完成。尚未完成的部分应清楚列出；单个 PR 合入不自动满足整体目标。

Issue 和 Project 用于展示和管理。同步失败不改变代码已经合入的事实，但用户明确要求的管理动作仍需完成。协调多个交付项的 Issue 必须等所需义务完成后再关闭，不能由其中一个 PR 自动关闭。

工作区、分支清理和本地 main 更新独立于代码交付。清理失败或暂缓不使已合入任务退回未交付，也不阻塞无关工作。main 更新按本地需要进行，不作为完成前提。

清理前确认准确仓库、路径、分支、预期提交和使用情况。保留有未提交或较新改动、仍在使用、共享或身份不明确的资源；不删除 main，不强制删除 worktree，不递归清空未知目录。删除引用须匹配预期 tip，执行后检查实际结果。只有确认可重建的缓存可以随清理丢弃。

## 6. 异常处理与操作保护

异常只阻塞依赖该信息或结果的动作。测试失败阻止合入，但允许在原范围内诊断、修复和重测；Project 不可用不停止普通开发；发布权限不足只阻止对应发布。说明具体失败、受影响动作和下一步，不把局部异常扩展为整个任务失效。

执行远程写入或破坏性操作前，确认目标仓库、环境、资源和当前状态，检查所需权限及用户限制。只读取当前动作需要的信息；执行后核实真实结果，不以本地日志、返回成功文本或生成文件代替服务器事实。

远程创建、更新或删除的结果不确定时，先查询并协调已有结果，再决定是否重试。不得盲目重复非幂等操作、覆盖用户内容或修改日志伪造成功。push、合入和删除引用使用准确目标及预期版本保护，避免影响并发的新工作。

部署、迁移和生产操作必须在已授权的目标、影响范围和限制内进行，并具备与风险相称的恢复办法。具体命令、环境参数和恢复步骤沿用适用环境的现有 runbook，例如[公开测试网部署与恢复](../../p2p/blockchain/public-testnet-governed-bootstrap.runbook.md)。遵守其中的技术安全约束，但不得借操作文档增加普通 PR 的通用审批或证据义务。

凭据和敏感运行数据不得写入仓库、公共日志或 PR 内容。权限不足、目标冲突或关键操作结果无法核实时，保留已有工作并停止依赖该条件的动作；其他已授权且不受影响的工作可以继续。
